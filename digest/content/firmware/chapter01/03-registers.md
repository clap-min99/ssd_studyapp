## 이번 레슨의 목표

`volatile`의 역할과 한계를 구별하고, 읽기-수정-쓰기의 경쟁을 추적합니다. 일반 R/W와 W1C 레지스터에 같은 코드를 쓰면 안 되는 이유를 설명합니다.

## 앞에서 배운 내용

`value |= mask`는 기존 값을 읽고 OR한 결과를 다시 씁니다. RAM에서 연산이 맞았더라도, 장치와 여러 실행 흐름이 관여하면 접근 규칙을 추가로 알아야 합니다. 여기의 장치는 모두 교육용 모델입니다.

## 개념과 동작

주변장치 레지스터는 설정·상태·명령을 담는 하드웨어 인터페이스입니다. 문서에는 주소뿐 아니라 다음 약속이 들어 있습니다.

| 규칙 | 읽기·쓰기 의미 |
| --- | --- |
| R/W | 문서가 허용하는 비트를 읽고 설정값으로 씀 |
| RO | 상태를 읽음. 쓰기로 설정하지 않음 |
| W1C | 1을 쓴 자리의 상태를 지움. 0을 쓴 자리는 유지 |
| 읽기 부작용 | 읽기가 상태 해제나 데이터 소비를 일으킬 수 있음 |

약어만 보고 모든 동작을 추측하지 않습니다. 예약 비트, 접근 폭, 연속 접근 순서도 레지스터별 설명을 확인해야 합니다.

**volatile 한정자**는 컴파일러에게 프로그램 밖에서 변할 수 있는 대상의 접근을 다루도록 알립니다. 일반 RAM 변수에 적용하는 것과 주변장치 헤더에서 사용하는 것을 구별해야 합니다. 정확한 접근 의미는 구현에 의존하며, volatile 접근이 하나의 하드웨어 명령이거나 원자적이라는 뜻은 아닙니다.

## 코드 읽기

아래는 일반 C11로 실행 가능한 RAM 예제입니다. volatile 문법을 설명할 뿐 하드웨어나 인터럽트를 재현하지는 않습니다.

```c
#include <stdint.h>
#include <assert.h>

int main(void)
{
    volatile uint32_t control = 0u;
    volatile uint32_t *reg = &control;
    *reg |= 1u << 3;
    uint32_t snapshot = *reg;
    assert(snapshot == 8u);
    return 0;
}
```

`volatile uint32_t *reg`는 volatile 대상에 접근하는 포인터입니다. `uint32_t * volatile reg`처럼 포인터 변수 자체를 volatile로 만드는 선언과 다릅니다.

`*reg |= 1u << 3`은 대상 읽기→OR 계산→대상 쓰기입니다. `snapshot`은 한 번 읽은 값의 복사본이므로, 나중에 장치가 바뀌어도 자동 갱신되지 않습니다.

실제 장치에서는 제조사 헤더가 타입·주소·필드 이름을 제공하는 경우가 많습니다. 예를 들어 CMSIS Cortex-M4 헤더의 `__IO`는 volatile로 정의되어 있습니다. 헤더를 쓰더라도 해당 레지스터의 부작용을 확인하는 일은 남습니다.

## 따라 풀기

**첫 번째 상황: 읽기-수정-쓰기(RMW) 경쟁.** 같은 설정값에 메인과 인터럽트 서비스 루틴(ISR)이 서로 다른 비트를 켠다고 가정합니다. ISR은 인터럽트가 발생했을 때 실행하는 함수라는 뜻으로만 알아두면 됩니다.

| 순서 | 실행 주체 | 동작 | 공유 설정값 |
| --- | --- | --- | --- |
| 1 | 메인 | 현재 값 0을 읽어 임시 보관 | 0x00 |
| 2 | ISR | 비트 1을 켜고 복귀 | 0x02 |
| 3 | 메인 | 임시 값 0에 비트 3을 켜서 씀 | 0x08 |

바라던 결과는 0x0A였지만 ISR의 변경을 잃었습니다. volatile을 붙여도 세 단계가 하나가 되지는 않습니다. 해결책은 공유 접근 설계에 따라 임계구역이나 장치가 제공하는 비트 설정·해제 전용 기능 등을 선택합니다. 인터럽트를 무조건 끄는 코드를 여기서 범용 처방으로 제시하지 않습니다.

**두 번째 상황: W1C 상태.** 비트 0과 1이 모두 1이고, 비트 0만 지우려 합니다. 아래는 실제 레지스터가 아닌 의사코드입니다.

```text
status |= 0x01   // 읽은 0x03을 다시 쓰므로 두 상태 모두 지움
status = 0x01    // 비트 0만 지움. 비트 1은 유지
```

W1C의 쓰기 값은 저장할 새 상태가 아니라 지울 비트를 지정합니다. 교육용 규칙으로 계산하면 `남은 상태 = 기존 상태 & ~쓰기값`입니다. 첫 방식은 0x00, 두 번째는 0x02가 됩니다. 이 규칙은 W1C에만 해당하며 다른 플래그 해제 방식에는 그대로 적용하지 않습니다.

## 헷갈리기 쉬운 점

- volatile은 락이 아닙니다. 원자성, 태스크 간 동기화, 캐시와 DMA의 일관성을 한꺼번에 해결하지 않습니다.
- 위 RAM 코드는 장치가 비동기로 바뀌는 현상을 검증하지 않습니다. 문법과 단일 흐름의 계산만 확인합니다.
- W1C 예제는 STM32의 모든 상태 레지스터에 대한 설명이 아닙니다. 0을 써서 지우거나 특정 읽기 순서를 요구하는 장치도 있습니다.
- 디버거의 레지스터 창도 읽기를 발생시킬 수 있습니다. 읽기 부작용이 있는 대상은 관찰이 동작을 바꾸는지 확인해야 합니다.

## 직접 확인하기

1. 위 RMW 경쟁에서 volatile이 있어도 결과가 0x08이 되는 이유는 무엇인가요?
2. W1C 상태가 0x0B일 때 0x02를 쓰면 어떤 값이 남나요?
3. snapshot을 반복 확인하는 코드가 장치 상태를 매번 새로 읽는 코드와 같은가요?

<details>
<summary>정답과 이유</summary>
<p>1. 읽은 값으로 계산하는 사이 ISR이 실행될 수 있습니다. 메인은 오래된 값에 근거해 덮어쓰므로 비트 1 변경을 잃습니다.</p>
<p>2. 0x09입니다. 0x0B는 비트 3·1·0이 켜져 있고, 쓰기 값은 비트 1만 지우도록 지정합니다.</p>
<p>3. 다릅니다. snapshot은 이미 복사한 일반 값입니다. 새 상태가 필요하면 규칙에 맞게 대상을 다시 읽어야 합니다.</p>
</details>
